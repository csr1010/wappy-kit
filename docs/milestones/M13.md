# M13 — Session profile: facts + current state, TTL-bound

**Spec:** §5 (state-ledger pattern this mirrors), §10 · **Depends on:** M12 (reuses its wrapped compose-response schema for zero-extra-call extraction) · **Tag:** `m13-done` · **Packages:** `@wappy/core`, `@wappy/harness`

**Goal:** A small, structured, per-contact profile that's read at the start of every inbound message and updated after every successful send, so the agent isn't only reasoning from the last message or a compressed rolling summary. Session-scoped only (resets after a TTL of inactivity); a global cross-session user profile is explicitly future work, not this milestone.

## Why this is a different thing from what already exists

- **`history-window.ts`'s rolling summary (M6)** is a permanent, ever-growing compression of old turns so the prompt fits budget. No expiry, no structured facts, triggered only when the raw turn count overflows — a context-budget mechanism, not a session-memory one.
- **`recentTurns` (M6)**, the last N turns verbatim, already goes into every prompt. Stays exactly as-is; the session profile is additive to it, not a replacement.
- **The 24h WhatsApp session window (M4)** is messaging *policy* (can we still send free-form), unrelated to memory content.

None of these capture "what did we ask the user that they haven't answered yet" or "what's this specific thread currently about, right now" in a way that survives a gap and doesn't go stale the way a compressed summary can.

## Design (confirmed with the user)

```ts
interface SessionProfile {
  contactId: string;
  facts: Record<string, string>;  // small, stable: name, phone, location. Not an open-ended store.
  currentState?: string;           // updated on EVERY turn — the fresh, open thread (a pending
                                    // question, what's being decided right now). Not compressed;
                                    // always reflects the latest state, which is what makes a short
                                    // reply like "medium" interpretable on its own.
  summary?: string;                // coarser session narrative, allowed to lag currentState
  expiresAt: number;                // epoch ms — TTL-bound; a fresh session starts once this passes
}
```

- **A new core interface, not an overload of `Memory`.** Same pattern already used for `SeenStore`/`SessionWindowTracker` in `@wappy/whatsapp` — one focused store per concern, not everything crammed into the general-purpose turn-history contract.
- **Backing store:** a new table in the same LibSQL client `createLibsqlMemory` already opens. Same database file a generated project already has; nothing new for a user to configure.
- **Read:** at the very start of handling an inbound message, alongside `Memory.load()`. If `now > expiresAt`, the profile is treated as expired — a fresh session starts with nothing carried over (facts/currentState/summary all reset).
- **Write:** after a successful send, the same point the reply gets persisted to `Memory`. TTL renews on every successful turn.
- **Extraction is free, not a second model call.** M12 already wraps the compose response schema to capture `formatRationale`. This extends that same wrapper: `{ formatRationale, sessionFacts?, sessionCurrentState?, sessionSummary?, message }`. The one compose call that decides format also updates the profile. This is the concrete reason this milestone depends on M12 rather than standing alone.
- **Feeds into the prompt as a new, small assembled section** (`assemble.ts` gains a `sessionProfile` input), alongside `recentTurns`, `summary` (M6's), `recalledSnippets`, etc. — bounded by the same context-budget mechanism everything else already goes through, not exempt from it.

## Tasks (sketch — not yet broken into T-numbers; do that at the start of implementation, once M12 is actually done and its exact wrapped-schema shape is real, not just planned)

- Core: `SessionProfileStore` interface (get/set/touch-expiry), `SessionProfile` type.
- Harness: `createLibsqlSessionProfileStore` (new table, same client pattern as `memory.ts`). Wire read at `handleOne`'s start, write after a successful send, reusing M12's extended wrapped schema for extraction.
- `assemble.ts`: new bounded prompt section for the profile's contents.
- Tests: TTL expiry (a profile past `expiresAt` is treated as absent, not returned); facts/currentState/summary survive a real round trip through the same compose call that also produces `formatRationale`; a short, ambiguous reply ("medium") composes sensibly when `currentState` describes a pending question (the actual scenario motivating this milestone) — a real behavioral test, not just plumbing.
