# M13 — Session profile: facts + current state, TTL-bound

**Spec:** §5 (state-ledger pattern this mirrors), §10 · **Depends on:** M12 (reuses its wrapped compose-response schema for zero-extra-call extraction) · **Tag:** `m13-done` · **Packages:** `@wappy/core`, `@wappy/harness`

**Goal:** A small, structured, per-contact profile that's read at the start of every inbound message and updated after every successful send, so the agent isn't only reasoning from the last message or a compressed rolling summary. Session-scoped only (resets after a TTL of inactivity); a global cross-session user profile is explicitly future work, not this milestone.

## Why this is a different thing from what already exists

- **`history-window.ts`'s rolling summary (M6)** is a permanent, ever-growing compression of old turns so the prompt fits budget. No expiry, no structured facts, triggered only when the raw turn count overflows — a context-budget mechanism, not a session-memory one.
- **`recentTurns` (M6)**, the last N turns verbatim, already goes into every prompt. Stays exactly as-is; the session profile is additive to it, not a replacement.
- **The 24h WhatsApp session window (M4)** is messaging *policy* (can we still send free-form), unrelated to memory content.

None of these capture "what did we ask the user that they haven't answered yet" or "what's this specific thread currently about, right now" in a way that survives a gap and doesn't go stale the way a compressed summary can.

## Design (confirmed with the user)

```ts
interface SessionProfile {
  contactId: string;
  facts: Record<string, string>;  // small, stable: name, phone, location. Not an open-ended store.
  currentState?: string;           // updated on EVERY turn — the fresh, open thread (a pending
                                    // question, what's being decided right now). Not compressed;
                                    // always reflects the latest state, which is what makes a short
                                    // reply like "medium" interpretable on its own.
  summary?: string;                // coarser session narrative, allowed to lag currentState
  expiresAt: number;                // epoch ms — TTL-bound; a fresh session starts once this passes
}
```

- **A new core interface, not an overload of `Memory`.** Same pattern already used for `SeenStore`/`SessionWindowTracker` in `@wappy/whatsapp` — one focused store per concern, not everything crammed into the general-purpose turn-history contract.
- **Backing store:** a new table in the same LibSQL client `createLibsqlMemory` already opens. Same database file a generated project already has; nothing new for a user to configure.
- **Read:** at the very start of handling an inbound message, alongside `Memory.load()`. If `now > expiresAt`, the profile is treated as expired — a fresh session starts with nothing carried over (facts/currentState/summary all reset).
- **Write:** after a successful send, the same point the reply gets persisted to `Memory`. TTL renews on every successful turn.
- **Extraction is free, not a second model call.** M12 already wraps the compose response schema to capture `formatRationale`. This extends that same wrapper: `{ formatRationale, sessionFacts?, sessionCurrentState?, sessionSummary?, message }`. The one compose call that decides format also updates the profile. This is the concrete reason this milestone depends on M12 rather than standing alone.
- **Feeds into the prompt as a new, small assembled section** (`assemble.ts` gains a `sessionProfile` input), alongside `recentTurns`, `summary` (M6's), `recalledSnippets`, etc. — bounded by the same context-budget mechanism everything else already goes through, not exempt from it.

## Tasks

### Core (`@wappy/core`)

- [x] **T13.1** `schemas.ts`: add `SessionProfileSchema` (zod) — `contactId: string`, `facts: record(string,string)`, `currentState?: string`, `summary?: string`, `expiresAt: number` — and its inferred `SessionProfile` type. `interfaces.ts`: add `SessionProfileStore` — `get(contactId, now): Promise<SessionProfile | undefined>` (undefined = missing OR expired, caller never sees a stale profile), `set(profile): Promise<void>` (upsert; caller always passes a fresh `expiresAt`, so a plain `set()` after every successful turn is also how the TTL renews — no separate "touch" verb needed, simpler than the original sketch). Export both from `index.ts`. Run `pnpm contract:update`; additive-only diff.

### Harness (`@wappy/harness`)

- [x] **T13.2** `session-profile.ts`: `createLibsqlSessionProfileStore` — new `session_profiles` table, same `Client`/`ensureSchema` pattern as `memory.ts`. `get()` returns `undefined` when the row is missing or `now > expiresAt` (expired rows aren't deleted eagerly — just treated as absent; a subsequent `set()` overwrites them same as any upsert).
- [x] **T13.3** `compose-with-budget.ts`: extend `ComposeResponseSchema` with optional `sessionFacts?: record(string,string)`, `sessionCurrentState?: string`, `sessionSummary?: string` alongside the existing `formatRationale`/`message` — zero extra model calls, same call that already produces `formatRationale`. `ComposeWithBudgetResult` gains the same three optional fields (absent on the fallback-degrade path, same as `formatRationale` falls back to a fixed placeholder there — no fabricated extraction).
- [x] **T13.4** `assemble.ts`: new optional `sessionProfile` input (rendered facts + currentState + summary as one small text block), budgeted and droppable like every other section — placed early in assembly order (right after `system`, before `skillFragments`) since it shapes how everything else should be read, and given a DROP_PRIORITY position just below `recentTurns` (second-hardest to drop) since a short reply like "medium" is only interpretable with `currentState` present.
- [x] **T13.5** `agent.ts`: new optional `sessionProfileStore?: SessionProfileStore` dep (unset = feature off, fully backward compatible). Read at `handleOne`'s very start, alongside `memory.load()` — `deps.clock.now()` for the TTL check. Pass its rendered contents into `composeWithBudget`'s `sessionProfile` input. After a successful send: merge `sessionFacts` into the existing facts (new keys win on conflict, nothing is ever dropped by omission), replace `currentState`/`summary` wholesale when the compose call returned them (kept as-is when it didn't — "allowed to lag", not forced to null every turn), stamp a fresh `expiresAt`, `set()` it. An expired-or-missing profile starts fresh (empty facts, no `currentState`/`summary`) — never carries stale state across a TTL reset.

## Tests introduced (`*.m13.test.ts`)

- Core: `SessionProfileSchema` round-trips valid shapes, rejects a malformed `facts` map.
- Harness (`session-profile.ts`): TTL expiry — a profile past `expiresAt` is treated as absent (`get()` returns `undefined`), not returned; `set()` after `get()` on an expired profile behaves as a plain upsert (no residual state leaks through).
- Harness (`compose-with-budget.ts`): `sessionFacts`/`sessionCurrentState`/`sessionSummary` survive a real round trip through the same compose call that also produces `formatRationale`; absent on the honest-degrade fallback path.
- Harness (`agent.ts`): a full turn with `sessionProfileStore` wired — facts merge (not replace) across two turns; `currentState` replaces wholesale; an expired profile is read as empty, not stale; nothing is read/written when `sessionProfileStore` is unset (backward compatible). The actual scenario motivating this milestone: a short, ambiguous reply ("medium") composes sensibly when a prior turn's `currentState` describes a pending question — a real behavioral test (scripted mock model asserting the prompt it received contained the `currentState` text), not just plumbing.
