- 2026-09-21: M8 code review round 1 — 2 HIGH, 2 MEDIUM, 2 LOW findings, all fixed. (1) HIGH — `shopify.ts`'s `getOrder` misrouted its own flagship scenario: the code's guard was `/^\d+$/.test(id) || id.startsWith("gid://")`, sending a bare digit string like `"8842"` (exactly what a model extracts from "where's my order 8842?") to a DIRECT `order(id:)` lookup using that digit string as Shopify's opaque internal numeric id — which it is not; that id is a large unrelated number. The in-code comment already stated the INTENDED behavior (bare digits should search by customer-facing order NUMBER) but the regex implemented the opposite. Fixed by removing the digit-string special case entirely — only an already-fully-qualified gid (`id.startsWith("gid://")`) takes the direct path now; everything else, including bare digits, searches by name. Updated/added tests in `shopify.m8.test.ts` and fixed `packages/e2e/src/spine-c.m8.test.ts`'s mock response shape (was `{order: {...}}`, now `{orders: {edges: [...]}}`) and assertion (was `{id: "gid://.../8842"}`, now `{q: 'name:"#8842"'}`) to match the corrected routing — this is the exact scenario spine C is supposed to prove works, and it was silently passing before only because the mock server didn't care what query shape it received. (2) HIGH — confirm-flow confused-deputy replay: `resolvePendingConfirmation()` only checked `message.selectionId === "confirm"`/`"cancel"` (bare constants) with no link to which SPECIFIC pending confirmation a button was generated for. Since `ConfirmFlow.request()` unconditionally supersedes an earlier unresolved confirmation for the same contact (one row per `contactId`), a real attack/accident scenario exists: agent asks to confirm action A (buttons sent, user doesn't answer), agent later asks to confirm a different action B (replacing A as the pending row), user's phone still shows A's stale buttons, a tap on "Confirm" there would execute B — an action never actually approved. Fixed by embedding the specific `PendingConfirmation.id` into the button's own `selectionId` (`confirmSelectionId(id)`/`cancelSelectionId(id)` → `"confirm:<id>"`/`"cancel:<id>"`, parsed back via `parseConfirmSelection()`) and comparing it against the CURRENT pending confirmation's id before acting; a mismatch replies "That confirmation isn't valid anymore" and leaves the current pending confirmation untouched (so a genuine reply to it still works later) rather than executing or discarding it. `invoke-tools.ts`'s `createToolInvoker()` now captures `confirmFlow.request()`'s return value and instructs the compose model to render buttons with the embedded-id selectionIds. (3) MEDIUM — Shopify search-filter injection: `getOrder`/`getInventoryLevels`/`lookupCustomer` built `query:` filter strings via raw template-literal concatenation of model-extracted values (e.g. `` `sku:${sku}` ``); a value like `X" OR sku:*` would widen the filter to match arbitrary records instead of the one asked about — not GraphQL document injection (variables were already correctly separated from the query document everywhere), but injection into Shopify's own search mini-language. Fixed with a `searchFilter(field, value)` helper that quotes and escapes the value (`field:"value"`, `"`/`\` escaped) before it's ever concatenated. (4) MEDIUM — `knowledge.ts`'s `splitLong()` could emit chunks exceeding `maxChunkChars`: after a forced split, the carried-over tail (`overlapChars` long) plus the next word could together exceed the limit on that very reassignment (e.g. `maxChunkChars:10, overlapChars:9` on `"abcde fghij klmno"` produced an 11-char chunk), violating the function's own documented contract. Fixed by capping the carried tail to `maxChunkChars - word.length - 1` so the reassignment can never overflow. Verified genuine (not just theoretical) by reverting the fix and confirming the exact regression test fails (11 > 10) before reapplying it. (5) LOW — `hardSlice()` would infinite-loop (or loop with a negative step) if `maxChunkChars <= 0` ever reached it; nothing validated the value. Fixed with a fail-loud guard at `chunkText()`'s entry point rather than deep inside the helper. (6) LOW — `decision.args` (model-controlled) was echoed unbounded into the confirmation-request summary/finding text fed to the downstream compose call — a prompt-injection-adjacent surface, though the reviewer noted actual tool execution still requires a genuine confirm tap so this could only mislead wording, not bypass the gate.
