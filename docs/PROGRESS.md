- 2026-09-21: M7 T7.0 parser choice: **`swagger2openapi@7.0.8`** (Swagger 2.0 → OpenAPI 3.x conversion) + **`@apidevtools/swagger-parser@13.1.0`** (OAS 3.x validation with pointer-level errors, and `$ref` bundling/dereferencing via its `@apidevtools/json-schema-ref-parser` dependency) + `@types/swagger2openapi` (swagger2openapi ships no types). Evaluated 3 options: (1) **oas-normalize** (readme.com) — an attractive all-in-one (detects version, converts 2.0→3.0, validates, dereferences) but pulls in `@readme/postman-to-openapi` for Postman-collection input, which is out of v0.1 scope (spec says "OpenAPI/Swagger... NO arbitrary-website discovery," and Postman collections aren't OpenAPI/Swagger either) — rejected for unnecessary dependency weight and scope creep. (2) Hand-rolled 2.0→3.x field mapping — rejected outright per T7.0's explicit "do not hand-roll" instruction; $ref resolution and schema-version conversion are exactly the class of finicky, edge-case-heavy logic a spec maintainer should own, not us. (3) **swagger2openapi + swagger-parser** (chosen) — each library does one job, both are the de facto standard tools in the OpenAPI ecosystem (swagger2openapi's author is an OpenAPI Initiative TSC member; swagger-parser is the most widely used JS OpenAPI parser/validator); swagger2openapi's last publish (2022) reflects the OAS 2.0 spec itself being frozen since 2017, not neglect. Design: load raw spec → if version 2.x, run `swagger2openapi.convert()` first so all downstream code only ever sees OpenAPI 3.x shape → `SwaggerParser.validate()` for schema validation (pointer-level errors) → `SwaggerParser.bundle()` (not `.dereference()`) to resolve only EXTERNAL `$ref`s while leaving internal `$ref` strings (including circular ones) as literal pointers, so T7.3's own depth-limited resolver — not the library — controls how deep circular/self-referential schemas get flattened into a Tool's JSON Schema `parameters`.
